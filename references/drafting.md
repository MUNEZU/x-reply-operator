# 成稿：用户观点 → 直接接原帖的日语回复

## 顺序

1. 读取原帖和必要父帖。用户贴出完整文字可作为输入，但不能虚构链接/作者/时间/互动。链接不可读且没有全文则请贴正文/截图，不靠 URL 猜内容。
2. 内部概括“原帖主张 → 用户回应 → 两者关联”。关联说不清不能成稿。用户未给观点时，可依据原帖提出不含个人经历的观察/自然追问稿，中文标“建议切入，非你的既有观点”；涉及核心价值判断且不能安全建议时，只问一个问题。
3. 提取原稿最有辨识度一点。三条观点不必全塞进去，其余可留后续；不同意见保留，不自动磨成客套话。
4. 检查因果：需求模糊与 SaaS 替换可讨论问题定义/验收；读懂代码与权限控制若无具体前提不能硬接。纠正概念、过度断言或无效因果时简短解释，核心立场会改变则询问。
5. 用“接原帖一句 → 具体解释/经历 → 有用判断”写短稿，自然日语优先于逐句翻译。默认不加产品名、框架缩写、自我推销或强行问句。
6. 检查公开边界、长度、语气和重复。未知使用效果不能写成「使って分かった」。

## 日本语气

- 简短具体，不堆「本質的に」「〜こそ重要」「〜と言えるでしょう」等抽象判断。
- 刺激点落在问题和行为，不把“中国/日本”“普通工程师/架构师”等群体简单分优劣。
- 局部观察用「自分が関わった案件では」「自分の経験では」限定，不推导全民趋势。
- 必要术语解释到普通读者能懂。一次回复不教完整个技术体系。
- 反问要自然可回应。幽默、负面共鸣、鲜明观点可以；事实错误和无关争吵不可以。

## 完成检查

- 一眼知道在回答原帖什么？一句话能概括观点？
- 是否多了用户没说过的经历、效果或绝对化判断？
- 关键态度是否保留，实质调整是否解释？
- 日本普通读者能理解场景/价值？
- 只有一条首选短稿，无标签与产品塞入？
- 长度已核验或明确保守估计，没有假称官方计数？
- 已回复线程确有新内容值得继续？

## 输出

**可直接复制的日语回复**：只放正文，不混编辑备注。

**为什么这样写**：中文解释接原帖哪一点、读者在意什么、保留/收窄什么。始终给一句长度状态：工具已核验（具体结果）或保守压缩、尚未经平台计数。关键待确认事实明确标出。

原帖无法获取、核心事实不足或逻辑不相接时，输出具体缺口与最多一个针对性问题，不硬给成品、不要求补一整份需求文档。
